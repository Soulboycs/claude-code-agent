# Codex 长时运行工程开发

当用户要求 Codex 持续开发一个非简单项目，并重视进度报告、严格测试、独立审查或诚实的发布结论时，使用本 Skill。

## 核心工作模式

把任务当作一个可持续运行的工程验证系统，而不是一次性生成代码。将工作拆成可观察的功能切片，并通过文件传递状态，使新的 agent 不依赖完整对话历史也能继续工作。

默认采用零信任的 **fail-closed（失败即拒绝放行）** 模型：其他 agent 的需求理解、实现、测试、review、日志摘要和结论都默认是潜在错误且潜在有害的，在独立验证前不可直接继承、合并或作为下一步依据。agent 之间互相同意不算证据。评估者可以否决生成者，第二个评估者也可以否决第一个评估者；最终结论只能来自可复现的契约、测试、运行时观察、数据库状态和记录清晰的推理。

## 代理启用决策

是否启用代理必须根据任务风险、独立验证的实际收益和代理成本决定，不能为了形式固定启动角色。**默认不启用子代理**，由主 agent 完成实现、测试和报告；主 agent 仍必须诚实说明验证范围和未验证内容。

### 必须考虑独立代理，但不自动启动

以下情况应先评估是否需要独立代理，而不是直接触发：

- 涉及两个或以上模块或跨模块状态链路；
- 涉及认证、授权、支付、隐私、迁移、队列、并发或外部供应商；
- 需要真实数据库、浏览器 E2E、生产配置或发布判断；
- 任务预计跨多个阶段、上下文或较长时间运行；
- 需求边界不清晰、错误代价高或难以回滚。

只有当主 agent 无法通过清晰的契约、可复现测试和可观察证据完成可信验证，或独立视角能显著发现主 agent 可能漏掉的问题时，才启动 reviewer/tester。任务不是长时任务，并不排除临时启用一个独立 reviewer；任务很复杂，也不自动意味着必须启用子代理。

### 必须启用的例外

仅在以下情况不需要再做成本权衡，直接启用独立代理：

- 用户明确要求多代理、对抗性测试或独立 review；
- 需要作不可逆或高影响的生产变更，且独立验证无法由主 agent 可靠完成；
- 发布门禁明确要求独立签字，而当前证据不能由同一 agent 自证。

### 建议启用独立代理

以下情况可按收益决定启用 Planner、Boundary Tester 或 Reviewer：

- 有两个以上可以并行且互不阻塞的子任务；
- 需要同时处理实现、测试、安全、性能或 UX 等不同专业关注点；
- 之前出现过假通过、回归、上下文丢失或代理自评过度乐观；
- 任务虽不高风险，但实现范围较大，独立拆分可以显著缩短时间或提高覆盖。

### 可以不启用代理

以下低风险任务通常由主 agent 直接完成即可：

- 解释、问答、只读分析或不改变状态的建议；
- 单文件、局部、可回滚的小修改，且已有测试能覆盖其边界；
- 文案、格式、注释或机械重命名等不改变运行行为的修改；
- 用户明确要求单 agent 处理，且任务不触发“必须启用”条件。

即使不启用代理，主 agent 仍应运行适当测试、检查 diff，并明确说明验证范围和未验证内容。

### 代理数量和角色按风险裁剪

不要求每个任务都启动四种角色。简单但有风险的修复可使用“Generator + 独立 Reviewer”；复杂跨模块任务再增加 Planner 和 Boundary Tester。每新增一个代理都要有明确的验证收益、输入边界和输出上限；没有独立问题要解决的代理不应启动。

## 代理角色

在允许并行代理且任务确实需要时，使用以下角色：

1. **Planner（规划代理）**：把简短需求扩展为范围、非目标、依赖、风险和验证计划。不要过早锁死不必要的底层实现细节。
2. **Generator（生成代理）**：一次实现一个功能切片，同时编写生产代码、针对性测试、诊断工具和必要文档。
3. **Boundary Tester（边界测试代理）**：主动寻找无效输入、超时、重试、竞态、并发、权限、注入、资源耗尽和外部供应商失败。
4. **Evaluator/Reviewer（独立评估代理）**：独立运行应用，检查 UI、API、数据库状态和日志，并审查测试是否真正覆盖被声称的行为。

关键发布门禁应取得三方独立 review，并记录分歧，不能用“多数同意”掩盖证据不足。

## 功能契约与 task 边界

实现一个功能切片前，先写出契约，至少包含：用户可观察行为和非目标；API、数据库、队列、缓存和状态机的预期变化；正常和负面路径；具体测试命令和环境；硬性通过/失败阈值；已知限制、回滚和补偿行为。

每个 task 在分派前都必须用可执行或可观察的检查定义边界：接受和拒绝的输入、输出与副作用、不变量、允许调用的依赖、禁止修改的资源、失败/超时/重试/并发/授权行为，以及允许下一个 task 开始前必须具备的证据。

测试是 task 能力边界的操作性定义。没有契约或测试明确规定的行为，不能默认为系统保证。代码存在、编译通过或作者声称完成，都不等于 task 完成。实现代理不能自行宣布发布就绪，必须经过独立评估。

## 结构化产物

优先在项目的 `docs/` 中维护以下文件：`SPEC.md`（需求和非目标）、`PLAN.md`（任务拆分和依赖）、`CONTRACT-<feature>.md`（可测试完成定义）、`TEST-MATRIX.md`（测试覆盖）、`PROGRESS.md`（动态进度）、`EVIDENCE.md`（命令和证据）、`TEST-QUALITY-AUDIT.md`（测试真实性审查）、`RISK-REGISTER.md`（风险和阻塞）、`RELEASE-GATE.md`（发布判断）和 `HANDOFF.md`（交接状态）。

不能删除失败历史。后续证据可以 supersede（取代）早期结论，但必须保留修正内容和原因。

产物必须小而可检查。每个文件或章节尽量只表达一个事实、决定或结果，并记录 task id、commit、命令、环境、时间、状态和证据链接。不要传递巨大 transcript、不可解释的生成文件或无限增长日志；应将其压缩为有边界的发现，同时保留原始证据路径。

## 双层可观测性

可观测性包含两个不可互相替代的层次：

1. **开发过程可观测性**：观察 Codex、agent、task、测试、review 和决策过程；
2. **应用运行可观测性**：观察代码运行后的日志、指标、trace、告警和业务状态。

### 开发过程可观测性

每个 task 和每个 agent 的工作都应留下结构化事件记录，使另一个 agent 或人类能够回答：谁在什么环境下做了什么、依据是什么、改变了什么、验证到哪里、为什么允许继续。

至少记录：`task_id`、`agent_role`、`run_id`、时间、当前 commit、工作区状态、输入契约版本、执行的命令/工具、修改文件、测试结果、失败原因、阻塞、下一步和证据路径。涉及外部依赖时，还要记录依赖名称、模拟/沙箱/真实环境、请求关联 id 和最终状态；禁止记录密钥、令牌和未经脱敏的个人数据。

日志分为三层：

1. **事件日志**：一条事件只描述一个动作或结果，例如 `test_started`、`file_changed`、`test_failed`、`review_rejected`、`gate_passed`；
2. **阶段摘要**：把一组事件压缩成小而可读的事实、决定和风险；
3. **原始证据**：完整命令输出、trace、截图或报告，放在有明确路径和保留期限的目录中。

agent 间默认传递阶段摘要和证据链接，不传递巨大 transcript。每个阶段开始和结束都要更新状态；长时间运行时定期记录心跳、当前 task、最近动作和是否阻塞。若 agent 中断或上下文重置，下一 agent 必须能仅凭日志和 `HANDOFF.md` 恢复，而不能猜测进度。

没有日志证明某个命令实际运行、某个测试实际失败/通过或某个文件实际修改时，不得把相应动作写入完成结论。

### 应用运行可观测性

只要 task 改变了运行时行为，就必须定义相应的应用可观测性契约，至少说明：

- 关键结构化日志、错误分类和关联 id；
- 关键业务指标、计数器、延迟和成功率；
- 跨服务或异步任务的 trace/span 和状态传播；
- 健康检查、就绪检查、队列积压和资源使用；
- 告警条件、阈值、责任人和处置路径；
- 业务状态是否能从数据库、队列或外部依赖中核对；
- 日志脱敏、保留期限、访问权限和成本边界。

必须通过测试或受控运行验证：正常请求可被关联追踪；失败、超时、重试和补偿可被区分；异步任务不会在日志中表现为“已发送”却无法确认最终状态；告警能够由可复现的故障触发并在恢复后关闭。开发过程日志不能替代应用运行可观测性，应用运行日志也不能替代 agent/task 的开发审计记录。

## 验证规则

按风险选择足够层级：单元测试、集成测试、真实数据库测试、API/浏览器 E2E、安全测试、对抗性测试，以及需要时的性能测试。真实数据库应验证约束、NULL、精度、并发和原子状态转换。

对每个关键测试检查：是否调用真实被测对象；被测代码坏掉时是否真的会失败；是否验证响应和副作用；是否覆盖反例；测试名称、层级和实际行为是否一致。重点识别绕过业务逻辑的测试、过度 mock、只断言“不抛异常”的测试和与实现共享错误假设的测试。

### 高价值测试门禁

测试必须以风险和信息价值为导向，而不是以数量或覆盖率为导向。每个关键测试都应明确：它要捕获的真实故障是什么、对应哪个边界或不变量、失败时能阻止什么后果、使用什么独立预期判断结果，以及失败后是否能快速定位。优先保留能验证用户可观察行为、数据一致性、安全边界、并发竞态、失败恢复和真实副作用的测试。

低价值测试包括：只重复同一场景、只验证实现细节、只断言“不抛异常”、完全依赖宽泛 mock、与实现共享同一计算逻辑、无法在实现损坏时失败、依赖脆弱时序或产生大量难以解释的快照。发现这类测试时应删除、重写或降级为非门禁检查，而不是继续增加测试数量。

在高风险功能上，必要时使用故障注入、变异测试或人工制造失败来确认测试确实能发现缺陷。测试套件应有清晰的门禁分层：阻断发布的高价值测试、用于诊断的辅助测试和仅供开发便利的检查，不能把三者混为一个绿色数字。

每次 task 转移都必须先独立审查上一个 task。只有契约测试和 review 证据通过，或人类明确接受并记录例外，才能进入下一步。review 必须具体指出失败用例、缺失断言、边界违反或可复现的通过理由。“看起来不错”、agent 共识和自写测试全绿都不够。

沙箱、契约、mock 和本地测试必须明确标记，不能被报告为真实短信、邮件、供应商、OAuth 或生产权限行为的证据。

## 进度报告

维护 `PROGRESS.md` 作为可追加的动态报告，至少包含：当前结论和具体证据；已完成工作；未完成事项和阻塞；通过/失败/跳过、环境和耗时；最新核验记录；被后续证据取代的历史结论及原因；以及当前证据明确不能证明什么。

使用精确状态：`已实现`、`单元验证通过`、`集成验证通过`、`沙箱 E2E 通过`、`真实依赖验证通过`、`生产门禁通过`、`有条件发布`、`生产验收未完成`、`阻塞`。

不能把“测试通过”写成“测试充分”，不能把“沙箱 E2E 通过”写成“生产通过”，也不能把本地性能样本写成生产容量承诺。

## 最终完成报告：触发时机、内容与边界

### 什么时候必须生成

在以下任一情况发生时，生成一份“最终诚实报告”作为本轮收口产物：

- 用户明确要求完成、收口、交付、上线评估或最终报告；
- 一个已定义的功能切片、里程碑、P0/P1 修复批次或跨模块链路完成；
- 计划中的任务已经执行到当前阶段的终点，需要决定是否进入下一阶段；
- 发布门禁评估完成，无论结论是可发布、有条件发布、生产验收未完成还是阻塞；
- 经过多轮失败和修复后，当前阶段暂时停止，需要固化已学到的内容和下一步。

普通中间进展只更新 `PROGRESS.md`，不必每条消息都生成完整最终报告。纯问答、只读分析、文案修改和没有运行行为变化的小修正，通常不触发该报告，除非用户明确要求。

### 报告必须呈现

当一个阶段、功能或项目完成时，必须额外生成一份类似“最终诚实报告”的收口文档，而不是只写一句“已完成”。报告至少包含：

- 初始声明/初始假设 vs 独立审查实际发现 vs 修复后状态；
- P0/P1 问题逐项状态，说明哪些功能本身正确、哪些测试或验证曾经不足；
- 每个关键问题的修复前、修复后、修改文件和验证证据；
- 测试数量变化、真实运行结果、环境、耗时、跳过项和限制；
- 代码、测试、集成、真实依赖和生产门禁各自达到的状态；
- 仍未闭环的风险、阻塞、补偿方案和不能宣称的结论；
- “学到了什么”：哪些原假设被推翻，为什么会漏测/误判，流程或 harness 做了什么改进；
- 历史结论校正：后续证据如何 supersede 早期结论。

“学习结果”必须来自实际失败、审查记录或可复现证据，不能写成泛泛的心得。最终报告应回答三个问题：我们原来以为是什么？实际发现了什么？现在凭什么认为已经达到当前门槛？

## 发布门禁

宣称“可发布”前，必须为相关项目提供证据：P0/P1 行为、测试真实性、迁移演练和 journal 登记、生产 ACL/RLS/默认权限、真实外部供应商、OAuth 回调、失败/重试/幂等/补偿路径、生产级性能、监控、日志脱敏、回滚方案和独立 review。

关键门禁缺失时，只能使用“生产验收未完成”“有条件发布”或“阻塞”等结论，不能声称“所有风险已消除”。

## Harness 持续维护

重要运行结束后检查 trace 和失败案例。只有在解决已观察到的问题或显著提高验证质量时，才保留某个 harness 组件。随着模型能力变化，重新评估 sprint 拆分、上下文重置和 evaluator 是否仍然必要；只有测量确认不会降低质量后，才简化流程。

本 Skill 只是工作流程，不授予对生产系统、真实供应商或其他外部系统执行变更的权限。需要外部副作用时，仍必须在实际操作前取得用户授权。
